## 1. Observed source audit
All source paths below are relative to app/src/main/java/com/apexfit/app/ at the pinned baseline. Reachability means the source navigation path exists, not that a device journey was tested.
- ProgressScreen -> ProgressOverviewContent Explore -> MuscleVolumeScreen -> MuscleVolumeSummary.calculate: Week/Month only; interactive ApexAnatomy front/back and ranked drill-down already exist (not a missing feature). HomeViewModel.completedSessions consumes FitnessRepositoryImpl.richSessionsFlow, which combines recent90DaySessionsFlow and recent90DaySetsFlow. Both date cutoffs are initialized once. Initial empty list may be presented as loaded. Yearly data cannot be safely inferred from this cache.
- SessionMapper.buildRichSessions has optional exerciseSecondaryMuscles default emptyMap; main richSessionsFlow calls with only sessions/sets. Secondary attribution is therefore missing on that path even though Exercise.secondaryMuscles and MuscleVolumeSummary support it. Mapper groups by exerciseId and discards row/session IDs, rest, units and segment identity. Do not reuse it for canonical reporting.
- ProgressScreen -> PersonalRecordsScreen uses ProgressViewModel.personalRecords -> FitnessDao.getPersonalRecordsWithNames. PersonalRecord key is exerciseId_type; WorkoutSessionManager.evaluatePRs calculates max_weight, volume, estimated_1rm; no source set/session ID, exact-rep dimension, or event history. PR date uses current local date while TrainingSession.date uses workout start day. Epley over all reps even one rep; corrections/backfill not verified. PR evaluation failure currently saves workout with no records; must be recoverable.
- ProgressScreen -> WorkoutHistoryScreen -> detail shows individual sets via DAO. ExerciseSet rows retain weight, reps, isWarmup, completed, restTaken, RPE, RIR and kg unit. No stable exercise occurrence or set timestamp persisted. Exercise performance graph entry point not verified; DAO getExerciseSetsByExerciseIdFlow exists, not proof of graph.
- WorkoutSessionManager.startSession/updateSet/commitRestTaken/addCustomSet find catalog exerciseId; WorkoutExecutionViewModel.loggedSets associates by exerciseId; repeated exercise occurrences collide. ActiveSession schemaVersion=1; ActiveSet completedAt exists but commit discards it. commitToDatabase allocates UUID on each invocation, persists session + PRs transactionally, then clears DataStore active JSON. A crash between commit and clear can leave retry risk; stable session ID is proposed. Important: FitnessDao.insertTrainingSession uses IGNORE and insertSessionWithPRsAtomic ignores its return value, then inserts sets. Reusing an ID alone would therefore duplicate sets on retry. WorkoutSessionManager.restoreJob clears JSON on version mismatch or parse error; persistSession debounces writes 500 ms. These are observed source risks, not device-reproduced failures.
- commitToDatabase stores partial sessions with completed=false/status=partial, yet saves completed sets and evaluates PRs. MuscleVolumeSummary excludes noncompleted sessions and recent DAO queries require completed session. Receipt and analytics can disagree. Proposed: include actual qualifying sets from saved partial workouts in training metrics, separate completion/adherence status. Existing recovery/progression behavior changes require review.
- WorkoutSchedule supports cycle weeks and anchor; WorkoutPlan/PlanSession edits and deletion mutate live schedule. TrainingSession.planSessionId alone does not preserve prior scheduled occurrences. No verified historical calendar. Rest classification in nextSession also needs review.
- WorkoutImportModels.supersetTag and WorkoutTextParser SUPERSET_FLATTENED preserve notes, no executable group. PlanExercise has sets/reps/rest/notes but no group or explicit order field; FitnessDao.getExercisesForSession orders by id ASC. Preserve that ordering in any migration. ActiveExercise lacks notes/group and set type. isWarmup boolean persists; no verified full advanced set flow.
- Body: ProgressScreen measurements and weight history, BodyWeightHistory.latest/daily and DAO observeAllWeightEntries support historical measurements. No relative-strength resolver, exercise goals or progress photo entry verified. Repository searches for PhotoPicker/goal and schema inspected; absence of search result is not proof all code is absent. Manifest allowBackup=false, FileProvider and INTERNET exist; privacy must be enforced by implementation, not assumed.
- Existing automatic volume adjustments, readiness and progression are separate from user-set target goals; preserve unless approved. Historical nutrition targets, save confirmation, weight fallback, timer and chart defects remain in master backlog.

## 2. Research and design decisions
Competitor evidence (official descriptions, not installed app tests):
- Hevy sets per muscle per week: https://www.hevyapp.com/features/sets-per-muscle-group-per-week/ ; monthly reports with source workout drill-through: https://www.hevyapp.com/features/monthly-report ; general stats/calendar: https://help.hevyapp.com/hc/en-us/articles/35702030346903-Hevy-Statistics-Explained-Track-Your-Training-Progress-and-Muscle-Growth .
- Fitbod weekly set targets: https://help.fitbod.me/hc/en-us/articles/24739986755223-Weekly-Set-Targets ; metrics and records: https://help.fitbod.me/hc/en-us/articles/12732749777047-Fitbod-Metrics-Records . These describe product behavior, not independent validation of the proprietary recommendations.
- Strong grouped exercises: https://help.strongapp.io/article/98-how-do-i-create-supersets ; set tags: https://help.strongapp.io/article/166-set-tags . No competitor behavior is treated as a scientific validation. Feature availability may depend on plan/platform; no exact paid-tier parity asserted.
Scientific evidence:
- Pelland et al., dose-response meta-regression, PMID 41343037: https://pubmed.ncbi.nlm.nih.gov/41343037/ . Fractional indirect-set counting had strongest relative evidence among tested methods; diminishing returns. Direct and secondary counts are counts of recorded bouts assigned using catalog metadata, not direct measurements of individual muscle stimulus. Fractional 0.5 is a population-model approximation, not validated individual dose. Do not ship fractional counts as the default or use them to drive target/progression changes; defer optional display pending approval.
- ACSM position stand 2026, PMID 41843416: https://pubmed.ncbi.nlm.nih.gov/41843416/ ; Currier et al. network meta-analysis PMID 37414459: https://pubmed.ncbi.nlm.nih.gov/37414459/ . Volume matters; no universally optimal individual weekly set count. Default targets unset; user may choose a target or opt in to clearly labeled broad guidance later. No algorithm silently changes prescriptions.
- Schoenfeld et al. frequency meta-analysis PMID 30558493: https://pubmed.ncbi.nlm.nih.gov/30558493/ . Frequency effect on hypertrophy not meaningful under matched volume; record distinct dates and actual gaps, don't score recovery from frequency alone.
- Nuzzo et al. reps/%1RM meta-regression PMID 37792272: https://pubmed.ncbi.nlm.nih.gov/37792272/ ; Reynolds et al. PMID 16937972: https://pubmed.ncbi.nlm.nih.gov/16937972/ . Rep-based predictions imperfect and exercise dependent. Proposed conservative e1RM rule: comparable external-load movements only; 2–10 contiguous reps Epley load*(1+reps/30), with explicitly rated RIR 0–2 eligible for the estimated record series. A single completed rep records achieved load, not a measured 1RM unless explicitly a maximal test; it may be shown as a conservative observed lower bound separately. Unknown or unconfirmed effort excluded from the new e1RM PR series, with historical load/rep charts intact. Existing ActiveSet/ExerciseSet default RIR=2 and RPE=0 mean defaults cannot be treated as evidence of effort; store nullable effort provenance for new logs. Self-reported RIR is imperfect (https://pubmed.ncbi.nlm.nih.gov/34542869/), and Epley is not universally validated for all movements (https://pmc.ncbi.nlm.nih.gov/articles/PMC9465738/). No extrapolation above 10, no RIR added automatically. The formula, eligibility, cutoff and any minimum freshness period are product policies, not proven universal thresholds. Preserve legacy records separately until reviewed; no formula change to existing progression.
- Drop sets meta-analysis PMID 37523092: https://pubmed.ncbi.nlm.nih.gov/37523092/ ; advanced systems review PMID 41718208: https://pubmed.ncbi.nlm.nih.gov/41718208/ . No validated conversion of each drop/rest-pause segment into an equivalent conventional hypertrophy set. Count a parent bout once, count segment reps/load separately; flag failure as effort outcome, not a bonus multiplier. These are reporting definitions, not biology.
- Android Photo Picker https://developer.android.com/training/data-storage/shared/photo-picker ; backup https://developer.android.com/identity/data/autobackup ; Room migrations https://developer.android.com/training/data-storage/room/migrating-db-versions ; database tests https://developer.android.com/training/data-storage/room/testing-db .
These are targeted evidence and product decisions, not a formal systematic review. Do not replace existing scientific algorithms wholesale.

## 4. Shared analytics architecture
Do not make 14 independent calculators. Proposed modules (names not existing): TrainingFactsRepository, TrainingAnalytics, StrengthAnalytics, RecordProjector, ScheduleLedger, GoalEvaluator, WeightAtWorkoutResolver, PhotoStore. Keep domain pure Kotlin, Clock/ZoneId injected, Room adapter and immutable typed UI state; no new paid services. Code layout may adapt existing package style after review.
- Truth: persisted workout_sessions/exercise_sets with stable session and occurrence IDs, set ID, actual canonical load/reps, explicit load basis, warm-up/type/failure, completion, actual rest, session-start local date + zone and timestamps; optional segments and muscle attribution captured at log time. Unknown remains null/unknown, not fabricated.
- Eligibility: saved completed qualifying set with positive reps, finite valid load for movement, not warm-up, not skipped; partial session sets contribute actual work but session is not full completion. Unrated effort stays unknown. Time/cardio and assistance are not forced into external-load calculations. Keep legacy behavior/version separate until migration approved. Direct primary muscle once, secondary distinct minus primary; totals across muscles not total physical sets. Snapshot new rows at commit; legacy secondary from current catalog only labeled inferred, unknown if absent; no false historical accuracy. Preserve existing primary recorded values.
- Time: inclusive start/exclusive end dates, local session start date frozen at creation, Monday calendar weeks, calendar months, explicitly named range buckets. Use injected date clock and refresh at midnight/timezone change; date-only legacy weights cannot establish same-day chronology unless time trustworthy; prefer earlier known date, expose uncertainty. No future records in current period. Distinguish no data, known zero, and unknown coverage.
- Load basis: canonical kg for stored mass, display conversion only. Record per-hand vs combined vs machine stack vs assistance vs bodyweight when explicitly known; legacy ambiguous remains unknown and comparison restricted to unchanged convention, with no invented conversion. Bodyweight reps and assistance tracked separately. Volume load is kg-reps (not mechanical work or muscle stimulus). Don't aggregate incompatible load bases into a misleading total; show separately or omit with reason. No assumption that machine stacks represent comparable resistance.
- Read facts via indexed bounded date queries joining sessions and sets transactionally, not 90-day readiness cache. Year/multi-year uses SQL aggregation where safe or streamed/paged facts; measure 100k-set fixture and explain query plans. Use same snapshot revision for chart/list/report. Loading/Error/Empty/Data typed separately; don't treat initial empty flow as loaded. Cache only derived data, keyed range, algorithm/attribution revision and DB invalidation. Never duplicate raw source-of-truth.
- Receipt: assign session UUID when session starts, durable active schema with migration; atomic idempotent commit persists actual sets, snapshots, schedule match and record projection/dirty marker. Within the same transaction explicitly check existing session and return persisted result or require insert succeeded; never blindly append sets after IGNORE. Stable occurrence/set keys and unique constraints protect new writes. Serialize commit and active-state changes; persist critical set completion and final snapshot durably, no 500 ms debounce-only durability claim. Retry same UUID returns same persisted receipt (no duplicate). Clear JSON after confirmed commit; recover crash between commit and clear via DB ID. Record timer-observed elapsed interval separately from prescribed countdown, pause time, skip and adjustments; cannot prove physiological rest or inactivity without observation. Use elapsedRealtime within boot, persist boot/session timing and flags; detect reboot/time jumps, unknown rather than invent. Reconcile set timestamps and source IDs. PR failure must roll back or mark projection pending and rebuild, never claim no PR if unknown.
- Records: deterministic chronological replay ordered by session local workout date then trustworthy session/set timestamps; fallback stable ID for deterministic display only, not actual time. Compare values at agreed canonical storage precision (round only for display; test lb/kg conversion tolerance), strict improvements and stable ties; same-day legacy ambiguity must be flagged; record events include metric, value, source session/set, rep count if applicable, policy version. Correct/delete invalidates affected exercise events and goals; rebuild transactionally, not permanent best-only record. Retain legacy PRs as archival unverified until rebuild; no invented source linkage.
- Calendar: immutable schedule version snapshots effective from explicit date/time; preserve past occurrence IDs and labels independent of plan deletion. Materialize bounded future window or derive from revision then freeze elapsed occurrences. All activation/edit/delete pathways must route same transaction; old unknown pre-feature calendar shows completed logs only. Rescheduling is explicit and auditably changes future occurrence; no auto miss on same day, skip/excuse explicit; mark missed only after a known planned date ends in the revision's explicit timezone and there is no linked full/partial completion or explicit excuse. Preserve partial as its own state; never count unknown coverage as missed. On same-day plan edit preserve completed/started occurrences; unstarted occurrence changes require explicit reschedule/replace semantics. Freeze historical local dates when traveling. Multiple same-day sessions linked individually; partial status separate; off-plan logs count training but not scheduled completion.
- Shared contract for Codex: range + filters => typed immutable analytics result with source IDs, coverage, data revision, units, count mode, calculation version; UI never recomputes domain metrics. Receipt, heatmap, graph, report, goal, PR consume same result/eligibility. Existing readiness/TDEE/progression remain independent until explicit parity review; centralize their inputs rather than changing formulas silently.
Example (external load, same convention): saved workout chest press 60x5, 50x10, warm-up 30x10; direct chest 2, secondary triceps 2, volume 800 kg-reps, exact rep PR candidates 60@5 and 50@10, estimated best 70 if both eligible. Receipt/chart/report same 2 working sets and 800, source IDs match; if partial, training work still 2, adherence status partial. Later deleting one set updates all projections, not just a chart.

## 7. Sanity-check addendum — 2026-11-27

### Additional release gates
- Source-confirmed: IGNORE insert + unconditional child insert, destructive active JSON mismatch recovery, debounced active writes, default RIR and best-only PRs. Tests must simulate failure after DB commit before DataStore clear, simultaneous finish attempts, process kill immediately after completion, restore v1 with duplicate exercise IDs, failed save preserving active state, and projection rebuild retry.
- Set definitions: completed working bouts are counts, not effective hypertrophy units. Existing effective-set score is explicitly a heuristic; preserve it and never present it as a measured growth outcome. Failure is subjective unless explicitly measured; not an automatic volume multiplier. Legacy unilateral load/rep convention unknown; do not silently multiply by 2. For new unilateral logs, record whether reps refer to one side or both only if known. Do not add separate left/right tracking to the 14-feature scope without approval.
- Historical record corrections: define earned-on-workout date vs recalculated-at timestamp separately. Only deterministic, source-linked historical events appear in reports. Do not announce a newly earned PR for backfill.
